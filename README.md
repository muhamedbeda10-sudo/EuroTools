# Eurotools — فحص الجودة / Quality Inspection

تطبيق تتبّع الجودة من **استلام الخامة حتى الإفراج النهائي**، بواجهة عربية (RTL)
وبيانات إنجليزية.

A quality-inspection app covering the full route from raw-material receiving
to final quality release. Arabic RTL UI, English data values.

## المسار (Process flow)

```
استلام الخامات (1)
        ↓
تحليل الخامة (2)  ──── عينات عشوائية تُقارن بالمواصفة
        ↓
      Roughing
        ↓
الفحص بعد الـ Roughing (3)        → Accepted / Rework / Rejected
        ↓
   Heat Treatment
        ↓
الفحص البصري + الصلادة (4)         → Accepted / Rejected / Further Investigation
        ↓
      Grinding
        ↓
الفحص بعد الـ Grinding (5)         → Accepted / Rework / Rejected
        ↓
      Finishing
        ↓
الفحص النهائي + CMM (6)            → Released / Rework / Rejected
        ↓
   الإفراج النهائي عن الجودة
```

## التشغيل محليًا

التطبيق يحتاج **Firebase emulators** فقط — لا قاعدة بيانات تُنصَّب ولا مفاتيح
خدمة، لأن الـ SDK يتعرّف على الـ emulators من متغيّرات البيئة ولا يطلب اعتمادات.
مفتاح خدمة لا تُنشئه أصلًا مستحيل يتسرّب.

في نافذة:

```bash
npm install
npm run emulators            # Firestore على 8080 وAuth على 9099
```

وفي نافذة أخرى:

```bash
cp .env.example .env
npm run seed                 # بيانات تجريبية تغطي كل المراحل
ADMIN_EMAIL=you@example.com ADMIN_PASSWORD='StrongPass123' \
  ADMIN_NAME='اسمك' npm run create-admin
npm run dev                  # http://localhost:3001
```

بيانات الـ seed تاريخية: حساباتها موقوفة وبمعرّفات صناعية، فلا أحد يدخل بها.
الحساب الحقيقي هو الذي ينشئه `create-admin`.

أوامر أخرى:

```bash
npm run test:run          # 105 اختبار وحدة للمنطق النقي
npm run test:rules        # 30 اختبارًا لقواعد الأمان، يحتاج الـ emulator
npm run test:integration  # ضمانات السلامة، يحتاج الـ emulator
npm run test:e2e          # 14 فحصًا في متصفّح حقيقي — انظر أعلى tests/e2e.mjs
npm run typecheck && npm run lint
npm run build             # يُخرج موقعًا ثابتًا في out/
npm run serve             # يقدّم out/ على 5000
```

| `/materials` · `/materials/view?id=` | المواصفات: مدى الصلادة، Ra، الشهادات المطلوبة، والخواص المقاسة لكل مرحلة |

## قواعد العمل (business rules)

كل القرارات تُتخذ في `lib/domain/` — دوال نقية بلا I/O، ومغطاة بالاختبارات:

- **الأبعاد**: تُقبل داخل `nominal − tolMinus … nominal + tolPlus` (الحدود نفسها مقبولة).
- **GD&T**: تُقبل داخل `0 … gdtLimit`؛ لا تُقرأ لها سماحية أبعاد إطلاقًا.
- **خاصية حرجة (Critical)** خارج السماحية → **رفض مباشر**، لا إعادة تشغيل.
- **الصلادة** أقل من المدى → رفض؛ أعلى من المدى → **فحص إضافي** (لا رفض).
- **كشف غير مكتمل** → الحالة تبقى `PENDING` ولا يتحرك الجزء — لكن أي عدم مطابقة
  مُسجَّلة تُحسم فورًا دون انتظار باقي البنود.
- **الاقتراح لا يُلزم الفاحص**: الواجهة تعرض النتيجة المقترحة وأسبابها، وللفاحص أن
  يختار حالة أخرى من الحالات المسموحة لتلك المرحلة فقط.
- **بوابات المسار**: الجزء لا يُفحص إلا في مرحلته الحالية؛ ولا تُصدر أجزاء من تشغيلة
  قبل قبول الاستلام واعتماد التحليل.
- كل إجابة بند وكل قياس يُحفظ منفصلًا (لا الحالة النهائية فقط)، ولذلك يستطيع تقرير
  «أكثر البنود تكرارًا في عدم المطابقة» أن يعمل أصلًا.

## الدخول والصلاحيات

الهوية من **Firebase Authentication**، والصلاحية من مستند المستخدم في Firestore
الذي مُعرِّفه هو الـ uid نفسه. إيقاف حساب يمنعه فورًا: القواعد تقرأ المستند في كل
عملية، فلا انتظار لانتهاء صلاحية رمز.

اسم الفاحص **لا يُكتب في النموذج** — يأتي من الجلسة، والقواعد تشترط أن يساوي
`inspectorUid` معرّف المتصل نفسه. يعني التوقيع باسم شخص آخر مرفوض من قاعدة
البيانات لا من الواجهة.

| العملية | مُطّلِع | فاحص | مشرف | مدير جودة | أدمن |
| --- | :-: | :-: | :-: | :-: | :-: |
| قراءة كل الصفحات والتقارير | ✓ | ✓ | ✓ | ✓ | ✓ |
| استلام تشغيلة وتسجيل الشهادات | ✗ | ✓ | ✓ | ✓ | ✓ |
| فتح تحليل وإدخال نتائجه | ✗ | ✓ | ✓ | ✓ | ✓ |
| تسجيل كشف مرحلة بالنتيجة المحسوبة | ✗ | ✓ | ✓ | ✓ | ✓ |
| **تجاوز** النتيجة المحسوبة | ✗ | ✗ | ✓ | ✓ | ✓ |
| إصدار أجزاء وإرجاع جزء للطابور | ✗ | ✗ | ✓ | ✓ | ✓ |
| **الإفراج النهائي** (`RELEASED`) | ✗ | ✗ | ✗ | ✓ | ✓ |
| تعديل المواصفات والسماحيات | ✗ | ✗ | ✗ | ✓ | ✓ |
| إدارة المستخدمين | ✗ | ✗ | ✗ | ✗ | ✓ |

خط الصلاحية مرسوم عند **التجاوز** لا عند التسجيل، لأن نتيجة الكشف مُشتقّة من
البنود والقياسات وليست مكتوبة: تسجيلها إثبات واقعة يقوم به أي فاحص، أما مخالفتها
فقرار يحتاج مشرفًا، والإفراج عن المنتج يحتاج مدير جودة.

المصفوفة كلها في `lib/domain/roles.ts` كدوال نقية، ومثبَّتة بالكامل في
`roles.test.ts` حتى لا تتوسّع صلاحية دون أن تظهر في الـ diff. الواجهة تستخدمها
لإخفاء ما لا يستطيع الحساب فعله.

لكن **الإخفاء ليس حماية**. الفحوص في `lib/client/actions.ts` تعمل على جهاز
المستخدم ويمكن إزالتها من الحزمة؛ هي موجودة ليُقال للشخص «لا تملك صلاحية» بالعربية
بدل أن يرى خطأ من Firestore. الحماية الفعلية في `firestore.rules` وحدها، وهي
مغطّاة بثلاثين اختبارًا تهاجمها من الخارج.

الحسابات **لا تُحذف أبدًا**، تُوقَف فقط: كل فحص موقَّع يجب أن يظل مشيرًا إلى صاحبه.
القواعد ترفض `delete` على `users` من أي حساب، فالضمان الذي كان قيدًا في قاعدة
بيانات علائقية صار قاعدة أمان. وتغييرات الصلاحيات تُسجَّل في `userAuditEvents`،
وهي هي الأخرى غير قابلة للتعديل أو الحذف.

الترقيم الفريد كان فهرسًا فريدًا، وصار مستند حجز مُعرِّفه هو القيمة نفسها: كاتبان
يتسابقان على رقم تشغيلة واحد يحاولان إنشاء نفس المستند، وواحد فقط ينجح — والقواعد
تمنع استبدال المستند بعد إنشائه. هذا مُختبَر بكتابتين متزامنتين فعليًا، لا
بمحاكاة.

## النشر على Firebase (الخطة المجانية)

التطبيق **موقع ثابت**: ملفات HTML وJavaScript تُقدَّم من Firebase Hosting،
وتتكلّم مع Firestore من المتصفّح مباشرة. لا يوجد خادم في الإنتاج على الإطلاق.

السبب: **App Hosting يتطلّب حساب فوترة**، ولا يعمل على خطة Spark المجانية. أما
Firebase Hosting للملفات الثابتة وFirestore وAuthentication فكلها تعمل على
Spark ضمن حصص يومية.

### ما الذي يتغيّر أمنيًا

هذه أهم فقرة في الملف. بدون خادم، **قواعد `firestore.rules` هي الحدّ الأمني
الوحيد** — لا يوجد شيء خلفها يلتقط ما تسمح به. اقرأ التعليق في أعلى ذلك الملف
قبل تعديله.

ما تفرضه القواعد، وبعضه **أقوى** مما كان:

- لا شيء إطلاقًا بدون حساب مُسجَّل هنا ونشط. حساب Firebase بلا مستند مستخدم،
  أو حساب موقوف، لا يقرأ ولا يكتب.
- **التوقيع مربوط بصاحبه**: الفحص لا يُكتب إلا و`inspectorUid` يساوي معرّف
  المتصل. التوقيع باسم غيرك مستحيل لا مجرد ممنوع.
- **الفحوص وسجل الحركة غير قابلة للتعديل أو الحذف** على مستوى قاعدة البيانات،
  ولا حتى من مدير النظام.
- **الإفراج النهائي** مقيَّد بالصلاحية، سواء جاء من فحص أو من تعديل حالة الجزء
  مباشرة.
- **الترقيم الفريد** محفوظ: مستند الحجز يُنشأ ولا يُستبدل أبدًا.
- الحسابات لا تُحذف، ومدير النظام لا يعدّل حسابه بنفسه.

وما **لا** تستطيع فرضه، مكتوب هنا صراحة بدل أن يُكتشف لاحقًا:

نتيجة الكشف **مُشتقّة** من البنود والقياسات بحسابات سماحيات وخواص حرجة ومدى
صلادة. لغة القواعد لا تعرف المرور على مصفوفة القياسات، فضلًا عن تكرار تلك
الحسابات. لذلك النتيجة تُحسب في المتصفّح ويكتبها المتصفّح، وصاحب حساب عبث
بالواجهة يستطيع تسجيل كشف نتيجته المخزّنة تخالف أدلّته.

الإفراج مقيَّد بالقواعد، فأخطر حالة مغطّاة. الباقي **يُكتشف بدل أن يُمنع**: كل
إجابة وكل قياس مخزّن بجوار الادعاء، والقاعدة نقية، فصفحة `/reports` تعيد اشتقاق
كل نتيجة وتسرد ما لا يطابق. راجع هذا التقرير دوريًا؛ وجود سطر فيه يعني أن السجل
لم يُكتب من التطبيق كما هو.

### 1 · المشروع

من Firebase Console أنشئ مشروعًا (خطة Spark تكفي)، ثم أنشئ قاعدة **Firestore**
في وضع Production واختر منطقة قريبة مثل `europe-west1`.

لا يوجد schema تنشئه: المجموعات تظهر عند أول كتابة، وبنيتها موصوفة بالكامل في
`lib/model.ts`.

**النسخ الاحتياطي**: جدولة النسخ التلقائي في Firestore تتطلّب Blaze. على Spark
صدّر البيانات دوريًا بنفسك — أبسط طريقة هي زر **تصدير CSV** في صفحة التقارير،
واحتفظ بالملف خارج المشروع. سجل الفحص مستند جودة يُطلب إثباته، وفقدانه ليس عطلًا
بل عدم مطابقة.

### 2 · قواعد الأمان والمصادقة

```bash
npx firebase login
npx firebase use YOUR_PROJECT_ID
npm run rules:deploy
```

ثم من Console فعّل **Authentication → Sign-in method → Email/Password**، ولا
تفعّل التسجيل الذاتي.

### 3 · أول حساب

على Spark بدون مفتاح خدمة، أنشئ الحساب من Console ثم امنحه الصلاحية:

1. **Authentication → Users → Add user** بالبريد وكلمة المرور، وانسخ الـ **UID**.
2. **Firestore → Start collection** باسم `users`، ومعرّف المستند هو الـ UID نفسه،
   وبالحقول: `email` و`displayName` نصًّا، و`role` بقيمة `ADMIN`، و`active`
   بقيمة `true` منطقية، و`signedInspections` بقيمة `0`.

بعدها ادخل بهذا الحساب وأنشئ باقي الحسابات من `/admin/users` — الصفحة تطلب الـ
UID من Console وتتولّى الباقي.

ولو كان معك مفتاح خدمة، السطر الواحد يغني عن ذلك كله:

```bash
ADMIN_EMAIL=qa.manager@example.com ADMIN_PASSWORD='...' \
ADMIN_NAME='م. منى رشاد' FIREBASE_PROJECT_ID=PROJECT_ID \
GOOGLE_APPLICATION_CREDENTIALS=/path/to/key.json npm run create-admin
```

لا تمرّر كلمة المرور كوسيط في سطر الأوامر؛ تظهر في تاريخ الطرفية.

### 4 · الإعداد والنشر

املأ قيم `NEXT_PUBLIC_FIREBASE_*` في `.env` من إعدادات تطبيق الويب في Console
(هذه القيم تصل المتصفّح بحكم التصميم، وهي تعرّف المشروع ولا تمنح شيئًا)، ثم:

```bash
npm run build
npx firebase deploy --only hosting,firestore:rules
```

### ما الذي يستهلك الحصة

الفحص الواحد كتابة **واحدة**، لأن بنود الكشف والقياسات مخزّنة داخل مستند الفحص
نفسه بدل خمستاشر مستند. والتقارير لا تقرأ كل الفحوص: العدّ بـ aggregation
queries، وترتيب البنود الأكثر رسوبًا من عدّاد يُحدَّث مع الفحص نفسه. الاستثناءان
المقصودان هما تصدير CSV وتقرير مطابقة النتائج، وكلاهما زر يضغطه أحدهم عمدًا.

الحصة اليومية على Spark ٥٠ ألف قراءة و٢٠ ألف كتابة. لو نفدت، **تتوقف الكتابة حتى
منتصف الليل بتوقيت المحيط الهادئ** — أي حوالي العاشرة صباحًا بتوقيت القاهرة. راقب
الاستهلاك في Console؛ إن اقترب من الحد، فترقية الخطة إلى Blaze تجعل التجاوز
يُحتسب قروشًا بدل أن يوقف الفاحصين في منتصف الوردية.

## البنية

```
app/                صفحات RTL (App Router) + تسجيل الدخول + الإدارة + التصدير
components/         ChecklistForm (قلب التطبيق) + عناصر واجهة مشتركة
lib/domain/         منطق نقي + اختباراته
                    stages.ts = مصدر الكشوف الوحيد
                    roles.ts  = مصدر الصلاحيات الوحيد
lib/model.ts        بنية المستندات — بلا أي SDK، يقرأها المتصفّح والسكربتات
lib/client/         Firestore وAuth والاستعلامات والكتابة، كلها في المتصفّح
lib/server/         Admin SDK للسكربتات فقط — لا يدخل حزمة الإنتاج
firestore.rules     الحدّ الأمني الوحيد
tests/              قواعد الأمان · ضمانات السلامة · متصفّح حقيقي
scripts/seed.ts     بيانات تجريبية
scripts/create-admin.ts  أول حساب
firebase.json       الاستضافة والترويسات
```

إضافة أو تعديل بند في أي كشف يتم من `lib/domain/stages.ts` وحده؛ الواجهة والتصدير
والتقارير تلتقط التغيير تلقائيًا. `key` هو ما يُخزَّن، فتغيير نص البند لا يُبطل السجلات
القديمة.
